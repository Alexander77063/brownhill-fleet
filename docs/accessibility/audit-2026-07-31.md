# Accessibility audit — Brownhill Fleet

**Original audit date:** 31 July 2026
**Re-verified in this fork:** 4 November 2026
**Target standard:** WCAG 2.1 Level AA
**Scope:** the Next.js application in `src/` — 193 TSX files covering the operations
console, the admin console, the accounting module, the finance console, the driver
portal, the investor portal, the public agreement-signing route and the legal pages.

> **How to read this document.** The findings below are the July 2026 audit of the
> project this fork descends from. The fixes are inherited: they are in this codebase.
> What was re-measured *here*, on 4 November 2026, is in
> [*What this fork re-verified*](#what-this-fork-re-verified-on-4-november-2026), and
> the two sets of numbers are not the same — this fork has grown pages the upstream
> audit never saw, and the runtime pass covers a different surface.

## Method — and its limits

Four checks run over the codebase. Three read source; one renders it.

| Check | Tool | What it proves |
|---|---|---|
| JSX a11y rules | `eslint-plugin-jsx-a11y` (strict) | ARIA misuse, label association, interactive-element misuse — zero findings |
| Form semantics | `scripts/a11y-audit.mjs` (TypeScript compiler API) | Every `<input>`/`<select>`/`<textarea>` resolves an accessible name — zero findings |
| Colour contrast | `tests/unit/a11y-contrast.test.ts` | Every design-token pair used for text clears 4.5:1, and UI borders clear 3:1 — 46 contrast-ratio assertions across 29 test cases, in both themes, computed from the tokens read out of `src/app/globals.css` |
| Runtime | `axe-core` 4.12 through Chromium (Playwright) | The real accessibility tree of 85 rendered pages — **97 axe scans across 85 pages** |

The runtime pass was restored in this fork on 1 November 2026. Upstream it was
`pnpm test:axe` against a local Supabase; here it is `pnpm test:a11y` against the
hosted stack from `hosted/dev/docker-compose.yml`, because the hosted deployment is
the product — it is the build the customer runs, it does not use Supabase Auth, and a
suite that ran against a different product would be scanning a different application.

**What is still NOT done.** No assistive-technology testing. Automated tooling — static
or runtime — catches perhaps a third to a half of WCAG issues by count. It confirms
that a name exists; it cannot confirm the name is *useful*, that a focus order is
*logical*, or that an error message *helps*.

**Consequence: this audit is still not sufficient evidence of AA conformance.** It
removes a specific, enumerated set of defects. Criteria depending on human judgement
remain *Not Evaluated* or *Partially Supports* in `VPAT.md` rather than assumed to
pass.

## What was already correct

Worth stating, because it is the reason the defect list is as short as it is. These
were verified and left alone — they are not padding in the fix list:

- A global `*:focus-visible` ring with `outline-offset`, applied app-wide.
- `@media (prefers-reduced-motion: reduce)` disabling the page-load reveal animation.
- `lang="en-GB"` on the document root.
- Decorative logos already carry `alt=""`; the icon set already sets `aria-hidden`.
- The password-visibility toggle already had both `aria-pressed` and `aria-label`.
- No click handlers on non-interactive elements anywhere in the codebase.
- The dark theme passed every contrast assertion without a single token change.

## Findings — 31 July 2026 (inherited)

Ordered by severity. "Instances" is the count of affected code sites, not screens.
These counts are the upstream audit's, taken on the codebase as it stood then.

### 1. Signature capture was pointer-only — Level A, 2.1.1 Keyboard

**The most serious finding.** On the public `/sign/[token]` route, a driver signs a
rental agreement by drawing on a `<canvas>` wired exclusively to
`onPointerDown/Move/Up`. There was no keyboard path, so a keyboard-only,
switch-access or severe-motor-impaired user could not execute a contract at all. This
is both a Level A failure and a contract-formation problem.

**Fixed:** added a "Draw it / Type it" choice. The typed path renders the name to the
same 520×170 PNG data URL, so the stored artefact and the API contract are unchanged.

### 2. 63 form controls had no accessible name — Level A, 4.1.2 / 3.3.2

Placeholder-only inline forms across bookings, finance, expenses, maintenance,
agreements, tracking zones, the CSV importer, both AI composers and the logo picker. A
placeholder is not an accessible name: it is not reliably exposed and it disappears
once typing starts.

**Fixed:** where visible caption text already existed but sat in a `<div>`/`<span>`,
the wrapper became a real `<label>` (agreements, finance — no visual change). Where no
visible label existed, an explicit `aria-label` was added. Controls repeated per table
row embed the row's identity, e.g. `Assign driver to booking ${reference}`.

> **Correction to an earlier count.** The first audit run reported 125 unlabelled
> controls. That was wrong. Seven page-local `Field` components render a real
> `<label>` around their children, which the tool could not see through. It now
> detects any component whose root element is a `<label>`, and the true figure is 63.
> No fix was applied to the 62 controls that were already correct.

### 3. Light-theme contrast failures — Level AA, 1.4.3

Ten token pairings failed. The dark theme passed cleanly and was not touched.

| Token | Was | Now | On page background |
|---|---|---|---|
| `--color-muted` | `#6b7688` | `#5f6a7c` | 4.07 → 4.85 |
| gold as text | `#9c7c1c` | `#7d6410` (new `--color-gold-text`) | 3.50 → 4.97 |
| `--color-profit` | `#3f9468` | `#2f7551` | 3.30 → 4.92 |
| `--color-loss` | `#c8463d` | `#b83c34` | 4.23 → 4.99 |
| `--color-warn` | `#b5831f` | `#8a6212` | 2.99 → 4.85 |
| `--color-info` | `#3f7fb3` | `#35719e` | 3.80 → 4.65 |

`--color-gold` could not simply be darkened: it is also the fill of the primary
button, whose dark label sits at 4.59:1 — darkening the fill would have pushed the
label *below* AA while fixing the text. A separate `--color-gold-text` token now
serves `.eyebrow` and table headers, leaving the decorative gold intact.

### 4. No way to bypass navigation — Level A, 2.4.1

Every authenticated page repeats a sidebar of links before the content. There was no
skip link anywhere in the app.

**Fixed:** a focus-visible skip link in `AppShell`, plus `id="main-content"` and
`tabIndex={-1}` on the `<main>` elements of the shell and the public pages.

### 5. Table semantics — Level A, 1.3.1 and 2.1.1

`scope` appeared **zero** times in the codebase. All 222 header cells across 41 tables
were ambiguous, so a screen reader reading a wide finance table announced values with
no column context. Separately, each table sits in an `overflow-x-auto` div that only a
mouse could scroll, stranding keyboard users on narrow viewports.

**Fixed:** `<Th>` now emits `scope="col"` by default — one change, every site that used
the primitive. `<Table>` now *requires* a `caption`, renders it as a visually-hidden
`<caption>`, and makes the scroll container focusable. In this fork 42 header cells are
hand-written `<th>` elements that the primitive never reached; they are counted below
and listed as a known issue in `VPAT.md`.

The container is deliberately **not** `role="region"`. An earlier revision of this
change used a named region, which is the pattern most often quoted for scrollable
containers — but `region` is a *landmark* role, so a named wrapper per table would
have injected a landmark per table into the screen-reader landmark rota. `tabIndex`
alone satisfies the keyboard criterion, and the `<caption>` provides the name.

### 6. Status messages were silent — Level AA, 4.1.3

The entire codebase contained exactly one live region. Sign-in errors, signature
validation errors and logo-upload errors all rendered into a plain `<p>` with no focus
change, so assistive-technology users received no feedback at all.

**Fixed:** `role="status"`/`role="alert"` wrappers, always rendered so the mutation is
observed, on the sign-in page, both signing flows and the logo uploader.

### 7. Heading structure — Level A, 1.3.1

- `CardTitle` hard-coded `<h3>` while pages render a single `<h1>`, skipping `<h2>`.
  Default is now `<h2>` with an `as` override.
- The login page's only `<h1>` lived in a `hidden lg:flex` brand panel, so **every
  mobile viewport had no `<h1>` at all**. "Welcome back" is now the `<h1>`; the
  marketing line became a styled `<p>`.

### 8. Navigation state and landmarks — 4.1.2 / 1.3.1

`aria-current` appeared zero times: the active nav item was conveyed by colour alone.
The sidebar and mobile bottom bar were also two unnamed sibling `<nav>` landmarks.

**Fixed:** `aria-current="page"` on active links in both navs; `aria-label` on the
`<nav>` elements.

### 9. Smaller items

- **1.3.5 Identify Input Purpose (AA):** added `autocomplete` to the sign-in email,
  phone, password and OTP fields, and the signing name fields. Deliberately *not*
  added to admin screens where staff enter a third party's details — 1.3.5 covers
  fields about the user.
- **2.4.7 Focus Visible (AA):** the signing page injects its own stylesheet and so
  never inherited the global focus ring. It now defines its own.
- **4.1.2:** the sign-in method tabs and the signature-mode buttons expose
  `aria-pressed`.

## The runtime pass — inherited findings, re-run here

Added upstream after the static remediation, it earned its keep immediately — it found
classes of defect that static analysis is structurally incapable of catching. Those
defects are fixed, and the fixes are inherited here.

### R1. Icon-only row links had no accessible name — 4.1.2, serious

`/ops/fleet`, `/ops/drivers` and `/ops/agreements` each rendered a chevron link in the
last cell of every row. The icon is `aria-hidden`, so the link had no name at all — axe
reported `link-name` on every row. Worse, the link was `opacity-0` until the row was
hovered, so a keyboard user focusing it saw nothing.

Static analysis missed this because the markup is a perfectly ordinary `<Link>` with a
child element; only the computed accessibility tree reveals the empty name.

**Fixed** by making the chevron decorative (`aria-hidden` + `tabIndex={-1}`). The first
cell of every one of those rows already links to the identical destination with a
proper name, so this removes a nameless duplicate link and a redundant, invisible tab
stop rather than inventing a label.

### R2. The password field's name was "Password Show" — 4.1.2

On `/login`, the password `<input>` and its Show/Hide toggle both sat inside one
`<label>`. The accessible name is computed from the label's entire text content, so the
field announced as "Password Show" — and flipped to "Password Hide" mid-interaction.

Every static check passed this: a label exists, and it is correctly associated. Only
asking the browser for the computed name exposes it. **Fixed** with explicit
`htmlFor`/`id` and the toggle moved outside the label element.

### R3. Six pages scrolled horizontally at 320 px — 1.4.10, AA

`/ops/fleet` overflowed by 5 px and `/ops/finance` by 29 px. The causes:

- A `grid-cols-3` stat row with no responsive variant, shared by **six** pages (fleet,
  drivers, agreements, billing, bookings, tracking). Only `/ops/fleet` tripped the
  threshold, because its numbers are widest — the other five were one long value away
  from failing. Now `grid-cols-2 sm:grid-cols-3`.
- The VAT return panel's quarter picker plus both download buttons on one non-wrapping
  row. Now `flex-wrap`.
- The permitted-zone form's three inputs at `grid-cols-3` behind a `pl-6` indent. Now
  stacks.

All ten reflow routes pass. The reflow test reports the offending selectors on
failure, because "the page is 29 px too wide" is not actionable on a page with a
thousand nodes.

### R4. The signed-in scans were silently scanning the consent page — 1 Aug

Running the suite in CI against a **fresh** database exposed something the local run
could not: the legal-consent gate bounces every authenticated route to `/legal/accept`
until an owner accepts the current `LEGAL_VERSION`. So the ops and driver scans were
not testing the pages they named — they were scanning the same consent page
repeatedly, and **passing**. A vacuous pass is worse than a failure, because it reads
as coverage.

Two causes, both fixed upstream: the demo tenant's most privileged member did not
carry `tenant.settings`, which the gate requires, so no member of a seeded tenant
could accept the terms; and the harness had no way to notice. `gotoAndSettle` now
asserts the final pathname is the route that was requested, so a redirect fails loudly
and names where it landed.

**This fork inherits the first fix** — `scripts/seed-auth.mjs` gives the operator
`tenant_admin`, which carries `tenant.settings` — and the harness here carries the
second, in `tests/a11y/helpers.ts`. The auth setup signs the operator in first and
clears the consent gate on the organisation's behalf before the other personas sign
in.

### R5. Keyboard-inaccessible scroller on `/ops/import` — 2.1.1, serious

The first defect found *because* of the fix above. Once CI actually reached the route,
axe reported `scrollable-region-focusable` on the CSV column-template preview: a
bespoke `overflow-x-auto` div rather than the `Table` primitive, so it never inherited
the keyboard fix the tables received. Its content is `whitespace-nowrap` and wider than
the panel, so without a mouse the right-hand columns were unreadable. Now focusable
and named.

### R6. The agreement-signing page — 1.3.1 and 1.4.3, five defects

`/sign/[token]` is public but unreachable without a valid token, so it sat outside the
runtime pass. Seeding a signing session and scanning it found the worst cluster in the
codebase — on the screen where a driver commits to a rental contract.

- **No heading at all (1.3.1).** The document title "Vehicle Rental Agreement" was a
  `<div>`. A screen-reader user landing on the link had nothing to orient on. Now an
  `<h1>`.
- **Four contrast failures (1.4.3).** This page renders its own stylesheet with
  hardcoded colours rather than the design tokens, so the token contrast test
  structurally could not see it:

  | Element | Was | Now |
  |---|---|---|
  | `.lbl` / `legend` — every field label | 3.72:1 | 4.85:1 |
  | `.foot` on the dark page background | 3.18:1 | 7.85:1 |
  | `.badge.ok` ("Signed") | 4.31:1 | 5.51:1 |
  | `.badge.wait` ("Awaiting partner") | 3.44:1 | 4.85:1 |

The signing palette is still outside the token test — that test reads
`src/app/globals.css`, and this page has a stylesheet of its own — so the runtime pass
is what keeps it honest: it scans the page on every run and the rendered pixels are
what axe measures.

### What the restored runtime pass found in this fork

The suite did not go green on its first run here: **44 passed, 56 failed**. Not
one of those failures was an accessibility violation. Four defects made whole
pages fail — three of them an HTTP 500 on a scanned page, the fourth a silent
write failure that bounced every authenticated route — and **none of them is
visible to a static check**, because a static audit reads the source of a page
that never renders.

With those four fixed, the second run came back **99 passed, 1 failed** — and
this time the failure was a genuine accessibility defect: a WCAG 1.4.10 Reflow
failure on `/ops/billing` at 320 CSS px. The static checks could not have found
that one either, for the same reason: they read the source and never lay the
page out.

With the Reflow defect fixed, the third run came back **100 passed, 0 failed**
— every scan clean, and the page that used to scroll sideways now fits inside
320 CSS px. That is the state this document describes, and it is the state the
`a11y` workflow will reproduce on every pull request — the fourth run, below,
confirmed it against a rebuilt image.

| Defect | What it did | Fix |
|---|---|---|
| `/admin/audit` embedded `profiles` through `audit_log.actor` | `audit_log.actor` is a foreign key to `auth.users`, and the `auth` schema is not one PostgREST exposes. The embed could never resolve, whatever the schema cache said: PGRST200, and the page returned 500 | The actor's email is resolved by a second query against `profiles`, keyed by the actor id |
| The two chart-of-accounts pages selected `normal_side` | The column is `normal_balance`; the select failed and both pages returned 500 | The select, its type and the cell all use `normal_balance` |
| The expenses form passed a plain function to `<form action>` | React refuses to serialise a function that is not a server action into a form, so the page failed to render at all | `submitExpenseAction` — a `'use server'` action in `src/lib/actions/expenses.ts` — replaces the page's local wrapper |
| PostgREST's schema cache was empty | Every write through it failed silently, and with it the legal-consent record | The compose stack starts PostgREST only after the bootstrap has applied the schema, and the bootstrap tells a running PostgREST to reload — see below |
| `/ops/billing` scrolled sideways at 320 CSS px | A cron command in a `<code>` element is one unbroken run of characters — a cron expression, two flags, a header and a URL — and it was wider than a 320 px window, so the whole page scrolled: 433 px of content in 320 px of viewport (WCAG 1.4.10 Reflow, Level AA) | The `<code>` breaks its text with `break-all`, the same remedy the product already uses for long tokens elsewhere |

The fourth is the one worth dwelling on, because it was hiding in plain sight and
it is a deployment defect rather than an application defect.

PostgREST reads the database schema **once**, at start-up, and caches it. The
compose stack started PostgREST as soon as Postgres was healthy — that is,
*before* the bootstrap oneshot had applied the schema — so its cache held no
tables at all. Reads keep working against a cache of nothing, because PostgREST
falls through to the database for a table it has never heard of, so the pages
rendered and looked populated. Writes did not: the legal-consent `INSERT`
answered 404 with an empty body, `recordLegalAcceptance` does not look at the
error, the tenant's acceptance was never recorded, and every operator route
redirected to `/legal/accept`.

Fifty-four of the suite's scans landed on that consent page instead of the page
they named. They **failed**, loudly, rather than passing quietly — which is the
one thing the harness has going for it. `gotoAndSettle` asserts that the final
pathname is the route that was requested, so a redirect names where it landed
instead of being counted as coverage of the page under test. That guard is the
fix upstream made for R4, and it is what turned a whole run of silent passes
into a whole run of named failures here.

The fix has two halves, because there are two ways to get this wrong:

- **A fresh stack.** PostgREST now depends on the bootstrap oneshot with
  `condition: service_completed_successfully`, so its first schema cache is the
  real schema. A healthy Postgres is not a ready schema.
- **A live stack.** On a deployed box PostgREST is a long-running service and
  the migrations are applied underneath it, so the dependency graph cannot help.
  The bootstrap now sends `NOTIFY pgrst, 'reload schema'` — PostgREST's own
  reload signal — after it applies the migrations.

Both halves are asserted by `hosted/tests/postgrest-schema-cache.sh`, which
runs in the `hosted-smoke` job on every pull request.

With that fixed, the **fourth** run came back **104 passed, 0 failed** — every
scan clean, and the consent page no longer swallowing fifty-four scans that
were meant for other pages. Two pages were added to the product between the
third run and this one, `/forgot-password` and `/reset-password`, and both are
in the scan list, so the coverage moved from 95 scans across 83 pages to **97
scans across 85 pages**. Every one of the 104 tests is accounted for by
`tests/unit/a11y-coverage.test.ts`: 97 axe scans, five setup tests and two
behavioural checks.

That run was made against the **rebuilt** application image, not against the
container that happened to be running. `next.config.ts` now sends
`Referrer-Policy: no-referrer` on `/reset-password` and `/sign/:path*`, and a
scan of the old image would have been a scan of something the product no
longer ships. That was checked rather than assumed — the running container was
asked for the header before the rebuild and did not send it, and sends it
after.

The fifth defect — the Reflow failure on `/ops/billing` — is the one that
argues for the runtime pass itself. A single unbreakable string in a `<code>`
element is not a rule violation in the source: the string is exactly what the
page means to say, and it reads perfectly well at a desktop width. It is only
when the viewport is 320 CSS px wide that the string is wider than the window
and the page has to be dragged sideways. Only a browser lays the page out, so
only a browser finds it — which is the whole argument for running axe and the
reflow measurement against the running application rather than against the
source.

## Recommended next steps

1. **Manual screen-reader pass** over the three flows that carry legal or financial
   weight: sign-in, agreement signing, and the VAT return. Now the highest-value
   remaining item — automation has taken this as far as it can.
2. **Remove the inner `<main>`** from the eleven admin accounting pages and
   `/admin/audit`.
3. **Zoom (1.4.4) and text spacing (1.4.12)** — a 200% zoom project alongside the
   existing 320 px one would be cheap now that the harness exists.
4. Keep `pnpm a11y` and `pnpm test:a11y` running so the fixed defects cannot silently
   return.

## Reproducing

```bash
pnpm install
pnpm a11y             # the three static checks (lint, form names, token contrast)

# The runtime pass — needs the hosted stack, the demo data and a password:
docker compose -f hosted/dev/docker-compose.yml up -d --build
bash hosted/scripts/wait-for-bootstrap.sh --compose-file hosted/dev/docker-compose.yml
docker compose -f hosted/dev/docker-compose.yml exec -T postgres \
  psql -v ON_ERROR_STOP=1 -U postgres -d postgres < supabase/seed.sql
SEED_PASSWORD='choose-one' node scripts/seed-auth.mjs
A11Y_BASE_URL=http://127.0.0.1:55431 \
DEPLOYMENT_PROFILE=hosted NEXT_PUBLIC_DEPLOYMENT_PROFILE=hosted \
SEED_PASSWORD='choose-one' pnpm test:a11y
```
