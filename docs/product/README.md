# Brownhill Fleet — product foundation

The ten documents every Brownhill Fleet project carries. This file is the
index: it says what each document is for, when it was last checked against
the code, and where its gaps are.

**Last audited against the code: 2026-11-05**, on `fix/gate-followup`, and
earlier on `feat/handover-hardening` (fork
`Alexander77063/brownhill-fleet`; fork base `7e1e458`, audited against
`16cf49d` and the changes committed alongside that audit), and again on
`fix/gate-followup` for the off-host backup
chain: the copy now has one implementation, a directory destination that
is compared with the dump, and a status page that says what was checked
rather than only that a copy was attempted — and again on the same branch on
2026-11-04 for the self-service password reset — and again on the same branch
on 2026-11-04 for the **audit trail**, which turned out to have been recording
nothing at all that the system did. The security review of that same date
then found two defects **in the reset itself**: it wrote no audit row, and
the email, the page and the redemption each decided the sign-in door
separately and had drifted. Both are fixed — one audit rule, one door rule —
and the audit now names the person rather than the service principal. The audit
below was carried out over four days — 2026-11-01, 2026-11-02, 2026-11-03
and 2026-11-04 — and the second day's findings are the ones that begin
*"On 2026-11-02"*, the third day's are the *"Fifth,"* near the end of
this section, and the fourth day's are the paragraph that begins
*"On 2026-11-04"* at the end of it. The migration
replay, the bootstrap idempotency gate, the environment-variable gate, the
bootstrap-waiter gate and the portability-guards gate below were all run
against a scratch Postgres on the same date. The portability proof and the
chain-assertion negative gate were run against the **live hosted stack** on
the same date — the first time assertion 14 (the TLS chain) or assertion 15
(the tenant-mismatch 403) have ever executed anywhere. The no-credential
gate, its negative gate and the acceptance bar's own arithmetic were run
against the working tree on the same date; the no-credential gate is the
first of the three that had never run at all, and its first run found a
rule in it that could not fail. The two restore gates — the one that proves
a restore survives the application's stop, and the one that proves the
privilege contract — were run against the working tree on the same date;
both had never run at all, and the first run of the first of them failed
against the restore script as it stood. The accessibility gates — the form
audit, the ESLint pass and the contrast test — were run against the working
tree on the same date; the contrast test had never existed, and the first run
of the contrast gate found a colour that failed AA. The three sign-in and
recovery gates — reachability, method choice and the operator's password
reset — were run against the working tree on the same date; all three had
never run at all, and each one found a defect on its first run: the sign-in
pages were unreachable, the hosted build offered a sign-in method it could
not honour, and a forgotten password had no recovery route inside the app.

On the same date the fixtures' stamp was found to be the clock and the
process id, so two fixtures built in the same second wore the same name,
and the isolation gate died on a unique-index violation before it could
prove anything at all. The stamp is now derived from the row's own id.

On the same date the accessibility suite was found to write the signed-in
session cookie to disk in a world-readable directory, where another local
user could read it and use it. It is now held at 0600, in a directory held
at 0700.

On **2026-11-01** the tree was audited again for the deployment's own
settings. Two new gates were written and run against the working tree, and
both found the defect they were written for on their first run: the settings
the application reads were not provided by anything on the box, under three
of the five names the handover gave, and the redirect pointed at a path the
application does not serve. The unit test for the password reset was
extended to 44 tests, covering the rule that a database which could not be
reached must raise rather than read as an empty table.

On the same date the **deployment gate** was audited, and it was the worst
of the three kinds of finding: a safety net with no call site. The table
that decides which URL prefixes a build does not serve had never been
consulted by anything, so the cross-tenant console, the SaaS's own signup
form and the subscription API were all reachable on a box that must serve
none of them. It is now wired into the middleware, with a 34-test boundary
and an 8-check negative gate. One prefix was **removed** from the table
rather than added: `/ops/billing` carries the operator's rent collection,
and gating it would have taken the arrears table, the driver's payment link
and the receipt form with it.

On the same date the **accounting module** was audited, and it turned up the
defect that matters most in this repository: a posting to the ledger could
leave half of itself behind. `accounting.journal_lines` carries a **deferred**
balance trigger, so an entry is judged at COMMIT and only there is the
balance meaningful — and the bridge was writing its entry, its lines and its
audit row as three separate autocommitted statements, so the trigger fired
after the **first** line, judged that line alone, and rejected the entry. The
entry row, committed before the lines were attempted, stayed behind as an
orphan with no lines. Measured against a real postgres:
`journal <id> unbalanced: debits=120 credits=0`. Three call sites took that
path — the reconciliation queue's "mark as a VAT payment" and "mark as a bank
fee" buttons, and the MTD VAT submission — and all three failed with a 500
while leaving the orphan behind. The bridge now takes a transaction handle as
a **required first argument**, so a call site that forgets one does not
compile. The same audit found that the accounting schema's tenant isolation
was **unproven**: migrations 0068 and 0069 had shipped policies that only
asked whether *some* tenant was pinned on the session and never compared the
row's tenant with the caller's — the same "a policy that merely looks right"
failure the migrations themselves describe. Both are now proved against a
real postgres, and the database-backed tests **actually run in CI** for the
first time.

On the same date the **chart of accounts** was audited, and it had a hole in
the middle of it. The ledger posts to a VAT Output account (`2200`) when a
VAT return is filed — and that account was **never seeded**, so the lookup
read `[0].id` off an empty result and died with `TypeError: Cannot read
properties of undefined (reading 'id')` *after HMRC had already accepted the
return*. The uniqueness that would have caught a duplicate was gone too:
migration 0069 replaced the global `unique (code)` with `unique (tenant_id,
code)`, and because NULLs are distinct in a unique index, **every global row
fell outside the constraint** — a second global code could be inserted at any
time, leaving a lookup by code with two answers and no way to choose. The
proof file that names these codes existed and **nothing ran it**, and its own
assertion was written as "is at least one of these six codes there?", so the
missing `2200` sat inside a green check. Migration 0083 seeds the account and
restores the global uniqueness on both `chart_of_accounts` and `vat_codes`;
every lookup now goes through one module that names the missing account
instead of crashing on `undefined`; and the MTD submission resolves its
accounts **before** it calls HMRC, so a chart of accounts that cannot carry
the posting stops the filing rather than orphaning a return HMRC has already
taken.

On the same date the **period close** was audited, and it turned up four
defects at once. The Close button shut a month with one click and no
warning, so an operator closing October with uncategorised bank lines and
an unfiled VAT return found out afterwards, when a posting came back 409 and
the month was already shut. The confirmation the dialog was supposed to ask
for was also **unusable**: it built its body as `{ period, confirm: true,
acknowledge }`, and `acknowledge` there was JavaScript's shorthand for a
variable of that name — which did not exist, because the state was called
`acknowledged`. What went over the wire was `acknowledge: undefined`, the
route read it as an empty list of acknowledgements, and **every** close was
refused with a 428. The operator could not close a period at all, and
nothing on screen said so, because the confirm button was correctly
disabled until the warnings were ticked. The warning it never showed was
also *wrong*: the preflight said a bank line posts into the month the bank
posted it, while the bridge posted an October line into the **current**
month — so an October line could still be categorised after October was
closed, and the warning was reassuring the operator about something that
could still happen. And the `period_opened`, `period_closed` and
`period_reopened` actions had been in the `accounting.audit_action` enum
since migration 0064 with **nothing ever writing them**: a month could be
closed and reopened with no record of who did it. The close now has **one**
HTTP surface — the old server action is gone, because two paths to the same
close is two ways to skip the confirmation — and it answers 428 with the
counts and the warnings, refusing a close whose warnings have not all been
acknowledged. The dialog and the route now build their bodies from one
module, so a renamed key stops both from compiling rather than silently
sending `undefined`. Each state change writes its audit row in the same
transaction as the change, so a close cannot land unrecorded. While that
trail was being written, its payload turned out to be **unreadable**:
`postgres.js` stringifies a `jsonb` parameter, so a payload that was
already a JSON string was stringified twice and landed as a JSON *string*
rather than a JSON *object* — the row looked healthy and
`after->>'sourceType'` read NULL.

On the same date the period close was audited **again**, and the thing it
had just been given was still a race. The close read the preflight in one
transaction and closed the month in another, with nothing between them: a
bank line dated in the month that landed in that window was never shown to
the operator, never acknowledged, and the month closed over it anyway. The
ledger was not corrupted — the posting guard still refuses a posting into a
closed period — but the **confirmation was a lie**. The close is now **one
transaction**: it takes a per-(tenant, period) Postgres advisory lock, and
every write that can change what it warns about takes the same lock — the
bank import and the journal posting — so the two are ordered rather than
racing. The acknowledgement now carries the **figures** the operator was
shown, not only the warning's name, because the name does not change when a
fourth bank line arrives: a name-only acknowledgement still matched, and the
month closed over a line nobody had seen. The bank writer became a module
(`src/lib/accounting/bank-import.ts`) that owns its own transaction,
precisely so that a caller cannot supply a transaction and forget the lock.
Both halves are proved against a real postgres by
`tests/integration/accounting/close-race.test.ts`, and the lock half was
watched **failing** with the lock removed from the writer.

On the same date the **HMRC submission** was audited a second time, by an
automated security review, and it turned up three findings that the first
audit had walked past. First, **a secret was passed on the command line**:
the test-token minter took the deployment's real signing secret as an
argument, and `/proc/<pid>/cmdline` is world-readable on Linux — so any
account on the box could read the box's signing secret out of the process
list while the proof or a chaos drill was running, and mint a session for
any user in any tenant. The secret now comes from the environment, where
only the process's own user and root can read it, and the minter has **no
fallback**: it used to sign with a fixed string that is committed in this
repository when no secret was in the environment, and because the middleware
does not verify signatures, that string produced a working session for any
user in any tenant, handed out without complaint to anyone who simply forgot
to set a variable. A missing secret is now a loud failure, and a durable
test proves the minter ignores a secret handed to it on the command line.
Second, **one tenant's VAT registration number could be filed against by
another**: the installation-wide number was a fallback at filing time, so a
tenant with no number of its own filed under whichever number the box
happened to carry — which may belong to a different organisation. It is now a
**default one tenant adopts**: the first tenant to connect adopts it and no
other tenant can take it afterwards, the filing path reads the tenant's own
column and nothing else, and the error raised when a number is already held
does not name the tenant that holds it. Third, **the same period could be
filed twice**: two submissions of the same month both created a submission
row and both reached HMRC, because nothing claimed the filing before the
call. The filing is now a **compare-and-set** — one claim per (tenant,
period) — so exactly one submission reaches HMRC, a second one is told the
return has already been filed, and a filing that never finished can be taken
over **only when the operator asks** to.

On the same date the **HMRC submission** was audited a third time, against the
two MEDIUM findings an automated review had raised about it, and **both were
real**. The first was that a return HMRC had **already accepted** could be
filed again: `pending_submission` meant two different things at once — "an
attempt is talking to HMRC" *and* "HMRC took it and the ledger entry has not
landed yet" — and the takeover path, which is what runs after a filing dies,
did not look at the correlation id that told the two apart. So a filing that
HMRC accepted and that then died before its journal entry landed left a row
saying "pending, never finished", and the deliberate "file it again" button
sent HMRC a **second** return for the same period — a duplicate return at
HMRC, and one organisation's figures counted twice. `accepted` is now a state
of its own: it is never taken over, and what it *can* do is have its ledger
entry completed, which is idempotent because the journal's key is
`(tenant_id, 'vat_submission', submission_id)`. The second finding was the
same shape one level down — the settlement addressed the row by id alone, so
a slow attempt could come back after a later one had taken the period over
and overwrite the row with its own answer. Every attempt now carries a
`claim_token`, and a settlement that does not present the current one changes
**nothing**.

The same audit turned up the way the VAT registration number's uniqueness was
**checked but not written**: two tenants saving the same number at the same
moment both read "nobody holds it" and both wrote it. The write is now under
an advisory lock that both writers take, and the holder check happens *inside*
that lock, so the second writer is refused with a named reason rather than an
exception; a partial unique index on `accounting.firs_credentials (vrn)` is
the backstop and refuses the second write whatever the application does. The
rule needed a second change to be true at all: the number could not stay
inside the credential upsert, because `on conflict (tenant_id) do update` only
handles a conflict on the index it names, and a concurrent conflict on the
**VRN** index is a different index — so it would have been an unhandled 23505
rather than a clean refusal. The number is written by its own `UPDATE` in the
same transaction instead.

And the **test suite** turned out to be a hazard of its own. The VAT
registration numbers the MTD tests use were written down in the source, so
every run wanted the same one: a run killed before its cleanup left a tenant
holding it, and the next run was then refused by the very rule it was
testing. It presented as a bug in the uniqueness check, and it had happened
twice on this box. The numbers are now derived from the run's own id, so a
dead run's leftovers are inert; and the cleanup runs each statement on its
own, because one statement tripping a foreign key used to skip every
statement after it and leave the whole tenant behind.

On the same date the **first-run window** was audited, and it was left armed
on the deployed box. `app_state.bootstrap_pending` was cleared in exactly one
place — the HMAC-signed `/api/v1/bootstrap` — and the second first-run
surface, `/api/auth/local/setup`, created the owner account and the tenant,
answered 200, and never touched the flag. The owner was real and the
application still believed it was waiting for its first run, with the
first-run door open behind the operator. The window is now closed inside the
same transaction that creates the owner: both doors close it, a setup that
cannot close it rolls back and fails rather than reporting success, and a
window that is stale on a box that already has an owner is corrected by the
server itself — the owner's next sign-in closes it — rather than by a
hand-written `UPDATE` on the customer's machine.

The same audit found a second defect in the same function, one layer down.
`createFirstUserAndTenant` asked `auth.users` whether an account already
existed, inside its transaction — but a transaction does not serialise two
CONCURRENT setups. Both could open one, both could read, both could see
nothing, and both could insert an owner, because the only thing that ordered
them was the `app_state` upsert at the END of the transaction, long after
both owners existed. The installation would then have had two tenants and two
owners on a product that is single-tenant by contract, and the operator would
have had to unpick it by hand. The setup now takes an **advisory lock before
the check it protects**, so the second setup waits for the first to commit and
then sees the account that was just committed, and refuses. It is the same
primitive the period close uses for the same reason, and the transaction
releases it — commit or rollback — so a setup that fails leaves nothing held.

On the same date the **ledger** was audited for the business it was supposed
to be keeping, and it was keeping none of it. The design spec names two
automatic posting rules — **Dr Trade Debtors (1100) / Cr Revenue (4000) / Cr
VAT Output (2200)** when an invoice is issued, and **Dr Bank / Cr Trade
Debtors (1100)** when a payment is confirmed — and both had a generator in
`src/lib/accounting/journal.ts` and **no call site anywhere in the product**.
The rent cron raised invoices; the payment ingest took money; neither wrote
to the ledger. So a live deployment's trial balance contained none of the
business it was running: it contained the handful of bank lines somebody had
reconciled by hand, and nothing else. The VAT return was worse than empty —
it reported **£0 of output VAT** against £40,000 of rentals, because
`public.invoices.vat_code_id` had been null on every invoice since migration
0067 and the return groups on it.

Four defects sat underneath that, and each is now fixed. The **period was
wrong**: `issued_on` was "the day the cron happened to run", so a six-month-old
agreement raised six months of rent on one day, all of it in this month's VAT
return. An invoice now carries the day it was issued — the rent week it bills,
which is also its due date — and its ledger entry lands in that month, so the
invoice, the trial balance, the VAT return and the receivables ageing all
agree. The **invoice and its ledger entry were two writes**, so a posting
refused by a closed period left the invoice behind; they are now **one
transaction**, and a bill the operator's accounts do not know about is not a
thing that can happen. The **VAT code was never resolved**, so every invoice
was invisible to the VAT return; it is now resolved *before* the invoice is
written, and a missing code is a named refusal rather than a null column. And
the **history was never restored**: a deployment that had been running for a
year already had its invoices and payments, and they had no ledger entries.
Migration 0086 posts them, into the month each document belongs to, and is
**idempotent** — a second run changes nothing — because a backfill that added
a *second* set of lines would double the business's revenue while every
individual posting still looked correct.

Measured against a seeded database, the migration restores what was missing:
**30 invoices and 28 payments posted, 58 journal entries, 146 lines, 58 audit
rows**, a trial balance that nets to **zero**, seven periods for seven
distinct document months and **no** posting in the wrong month — and the VAT
return goes from **£0 of output VAT to £5,100**, against £25,500 of net sales.

On the same date the **invoice void** was built, and the product had **no way
to cancel an invoice at all** — there was no invoice list anywhere in the
product (an invoice was visible only in the reconciliation queue's match picker
and in the reports), so a correction the operator could not see was a
correction nobody could perform. There is now a register at
`/accounts/accounting/invoices` and `/admin/accounting/invoices`, and a void
that is **a reversal, not a status change**: it posts into the **invoice's own
month** — a March invoice voided in November belongs to March — and the credit
is **split**, because a plain mirror is wrong for a paid invoice. The payment
already credited Trade Debtors by the gross, so a second credit would leave
the account at **−gross**, a negative asset. A paid invoice's credit is
therefore Cr Trade Debtors (gross − received) + Cr Refunds Payable (2120,
received), and the refund is money the business owes back rather than revenue
it never had. The whole void is **one transaction** — the invoice lock, the
reversal, the status change and the `invoice_voided` audit row — and it takes
the invoice's lock **before** the period's, the same order the rent cron
already takes, so the two cannot deadlock. A closed period is refused with a
409 naming the month; a second void is refused without posting anything; and
another tenant's invoice reads as *not found* rather than as a leak. No
migration was needed: `journal_source_type` already carried `invoice_void`,
`audit_action` already carried `invoice_voided`, and 2120 was already seeded.

On **2026-11-02** the tree was audited again, this time by running it. Four
things came out of it.

The **scheduled jobs** came first, and the finding was that the box had
**none**. `CRON_SECRET` was provisioned nowhere, so every `/api/cron/*` call
answered 401 — `isCronAuthorized` fails closed when the secret is unset in
production, which is right, and it meant the box was silent rather than open.
And nothing called the routes: the only three `.timer` files on the box were
the backup, the backup verify and the certbot renewal. The consequence was not
a slow box but a box that **billed nobody** — `/api/cron/generate-rent` is what
raises the weekly rent invoice, so no invoice was ever raised, the ledger's
revenue column stayed empty, the VAT return reported nothing and the
receivables never aged. There are now eight timers, one per application cron,
over a `brownhill-cron@.service` template that runs
`hosted/scripts/brownhill-cron.mjs`, and `hosted/tests/cron-timers.sh` holds
the whole arrangement in place — including a negative gate that removes a timer
and requires the gate to notice.

Second, six test files sat under `hosted/tests/`, which **vitest does not
collect**: they were written, they looked right, and they had never been
executed. Two could not have passed anyway — the lockout test inserted the
literal ids `'u-new'` and `'u-old'` into `auth.users`, whose `id` is a `uuid`,
and seeded the credential with the string `'placeholder-hash'` — so the
sign-in lockout, the only thing standing between a guessable password and the
operator's own console, had **no test anywhere**. It does now, proved end to
end against a real postgres, including the half that matters most: while the
lock holds, even the **correct** password is refused, because the lock is on
the account and not on the attempt.

Third, the accessibility programme could only ever have found pages that
*render*. It scans; it never changes anything, so nothing in it could catch a
flow that renders perfectly and submits nothing. The **live handover pass**
(`tests/live/handover.spec.ts`, its own Playwright config, its own command) now
drives the two flows that turn a row into a person who can sign in: the
operator invites a colleague, the colleague signs in with the on-screen
password, the operator invites a driver, the driver signs in, and the operator
sees the invited driver in the drivers list.

Fourth, the **build** had a third party in it. `next/font/google` fetches the
font CSS and the font binaries from Google **while the image is being built**,
and the hosted image build died on 2026-11-01 with a null dereference inside
Next's own font loader, on a branch whose source had not changed. The
customer's box builds the application when it updates, so this was never only
a CI problem: a VPS that could not reach Google Fonts that minute could not be
updated, and there was nothing on the box to fall back to. The three woff2
files are now in the repository and the module uses `next/font/local`, and
`tests/unit/offline-fonts.test.ts` holds the rule that nothing under `src/`
may go back to the network.

Fifth, a **race** was making the hosted job fail at random. The postgres image
does not start one server: it starts a **temporary** one to run `initdb`,
shuts it down, and only then starts the real one — and the temporary one is
started with `listen_addresses=''`, so it answers on the unix socket and on
nothing else. `psql` connects over the socket unless it is told otherwise, so
a readiness probe running `psql -c 'SELECT 1'` is answered YES by a server
that is about to be shut down under it. The gate declares the database ready,
the next command arrives, and the server has gone. The failure that follows
names the wrong thing — *"the throwaway postgres never came up"*.

It lost **once**, and the failure is worth reading for what it says. The seed
gate had a thirty-second budget. It failed in 0.98 of them, before a single
assertion had run, with `Result: 0 passed, 0 failed`. A probe with thirty
seconds to wait does not time out in one — so the probe had *succeeded*:
something answered, and the line after it found the server gone. The only
server in that container that comes and goes is the temporary one. Across
this repository's whole CI history — seventy runs, twenty-four of them red —
the race produced exactly one red build. (The other red builds that week
were three *different* defects: the build-time font fetch, a fixture-name
collision and the environment-variable spelling.) Which is exactly why it was
worth fixing anyway: the defect sat in five places, and the four that had not
yet fired would have fired on the customer's own box, where there is no CI
to re-run.

The place that papered over it was the worst of them: the portability proof
probed the socket and required two consecutive successes, which clears the
restart only if the temporary server shuts down between two probes — and
`initdb` routinely takes longer than the probe interval. That was the same
race with a longer fuse, in the one script that certifies the deployment is
fit to hand over. The rule is now written once, in
`scripts/lib/postgres-container.sh`, and it asks for **127.0.0.1**: the real
server is the first to listen there and the temporary one never does. Five
callers use it — the seed gate, the migrations-regression gate, the
bootstrap-idempotency gate, the portability proof and the compose healthcheck
— and `hosted/tests/postgres-readiness-probe.sh` holds all five to it.

On **2026-11-04** the tree was audited again, this time for the people the
product's own **staff** are not: the drivers, the members and the vehicle
owners. They had a password and a way to sign in with it, and no way to get
back in when they forgot it — the recovery route was the operator, on the
telephone, which is a real route but not one anybody can use at eleven at
night. And both portal sign-in pages carried a "Forgot password?" link
pointing at a page **behind their own layout**, so a locked-out user was
bounced straight back to the sign-in form, in a loop, with no way out.

There is now a self-service route: `/forgot-password` asks for an address,
`/reset-password` redeems a token, and the person ends at the sign-in page
that matches their role — a driver is not sent back to the staff door and
then bounced by the role check. The design is shaped by one rule: the answer
is the **same** for every account state, because a page that says
"no such account" hands out the customer list, and the person most likely to
be running that is the person trying to take one over. Only the **hash** of
the token reaches the database, which is on the customer's own box; the
redemption sets the password and spends the token in **one** statement that
is **conditional on the token being redeemed still being the live one**, so a
forwarded link is not good twice — including when two redemptions of it are in
flight at the same moment, which is the case the condition exists for and the
case a one-statement write alone does not cover. It also takes the account's
row locks first, so it cannot interleave with a sign-in that is verifying the
old password.

Two things about that route were wrong, and the security review of 2026-11-04
found both. The reset wrote **no audit row**, although the operator's reset
wrote one and the user flow says every reset is audited — so the trail had no
record of the one thing a person does to their own account that an
administrator might have to answer for. And the three places that decide which
sign-in door a person ends at each worked it out **separately**, and drifted:
the email ignored the build and pointed a vehicle owner at `/owner/login` on a
build that does not serve that page, the reset page kept a private copy of
the rule, and the redemption answered only "ok", so the browser used the
door the **link** named — which can be half an hour out of date.

Both are now single rules. The door comes from the account's role **read at
the redemption**, and the build is a required argument to the rule, so a
caller that forgets to say which build it is on fails to compile rather than
guess. The reset is audited as `member.password_reset`, filed under every
tenant the account belongs to — one credential opens the account in all of
them — and attributed to the **person**, who proved control of the address on
file by reading the link that was sent there. The feature is proved by 175
unit tests across eleven files and fourteen integration tests against a real
Postgres, and both new pages are in the accessibility scan list, which moves
the published coverage from 95 axe scans across 83 pages to **97 across 85**.

On the same date the **audit trail** was audited, and it turned out to have
been **empty of everything the system did**. `audit_log.actor` carries a
foreign key to `auth.users(id)`, and `log_audit()` defaulted that column to
the user the request was made for — which, for a request made by the
*server*, is the service principal, and the service principal is deliberately
not a user, because an audit row attributing a cron job to a named employee
would be a lie. So every system write was refused by the foreign key, and
twenty-four of the twenty-eight call sites threw the refusal away: the trail
did not fail, it was silently never written, and the only symptom was an
empty table.

A system action is now recorded with **no actor** — the shape the audit page
has always rendered as "system" — and an action is never lost because its
actor could not be established. The write also goes through **one** writer
now, and that writer looks at the error; a contract test fails the build if
any module writes an audit row by hand.

The rule for "real credentials" is the production script's own — empty, or a value starting with `REPLACE_` — and the gate drives the **production** function against the same files, so the two cannot drift | **Enforced by CI** — the `hosted-smoke` job, on every pull request that touches `hosted/**`; 27 assertions in the gate, green 2026-11-03. The gate was proved to bite twice: deleting the placeholder rule from the module fails it in nine places, and putting the old unguarded drill in front of it fails it — and the gate **refuses to run an unguarded drill at all**, because running one would put a stub in `/usr/local/bin` |
| Every wait for a containerised postgres goes over TCP | `scripts/lib/postgres-container.sh` and `hosted/tests/postgres-readiness-probe.sh` — the postgres image does not start one server: it starts a **temporary** one to run `initdb`, shuts it down, and only then starts the real one, and the temporary one is started with `listen_addresses=''`, so it answers on the unix socket and on nothing else. `psql` connects over the socket unless it is told otherwise, so a readiness probe running `psql -c 'SELECT 1'` is answered YES by a server that is about to be shut down under it: the gate declares the database ready, the next command arrives, and the server has gone. The failure that follows names the wrong thing — *"the throwaway postgres never came up"*. It is a race, so a green run is not evidence that it is gone, and it lost exactly once in this repository's CI history: the seed gate on 2026-11-03, which had a thirty-second budget and failed in 0.98 of them, before a single assertion had run, with `Result: 0 passed, 0 failed` — so the probe had succeeded, and the line after it found the server gone. The other red builds that week were three *different* defects, not this one. What made it worth fixing anyway is that the defect sat in five places, and the four that had not yet fired would have fired on the customer's own box. The place that papered over it was the worst of them — the portability proof probed the socket and required two consecutive successes, which clears the restart only if the temporary server shuts down between two probes, and `initdb` routinely takes longer than the probe interval. That was the same race with a longer fuse, in the one script that certifies the deployment is fit to hand over. The rule is now written once, in `scripts/lib/postgres-container.sh`, and it asks for **127.0.0.1**: the real server is the first to listen there and the temporary one never does. Five callers use it — the seed gate, the migrations-regression gate, the bootstrap-idempotency gate, the portability proof and the compose healthcheck — and the gate holds all five to it: the shared rule asks for TCP, every script that starts a postgres waits with that rule, no script carries a probe of its own, and every compose readiness probe names a TCP host | **Enforced by CI** — the `hosted-smoke` job, on every pull request that touches `hosted/**` or `standalone/**`; 14 assertions in the gate and 6 in the negative gate, green 2026-11-03. The gate was proved to bite: five defects injected into fresh copies of the tree — the compose healthcheck back on the socket, a gate that stops using the shared rule, a gate that stops using the shared wait, a gate that probes postgres itself, and the shared rule losing its TCP host — each make it fail, and it is required to pass against an unmodified copy first, so that a gate broken for any other reason cannot satisfy the negative gate |
| The deployment applies the migrations, or it does not deploy | `hosted/tests/deploy-applies-migrations.sh` — the documented update path was `git pull origin main && ./hosted/scripts/deploy-app.sh`, and it shipped code against a schema the database did not have: the deploy built the application, copied it into place and restarted the service, and never applied a migration. Migration 0088 added `password_reset_requests` — the table the self-service password reset writes its throttle to — and the deployment of that feature answered `ERROR: relation "password_reset_requests" does not exist` to the one screen a locked-out person has. The gate runs the **real** deploy, the **real** bootstrap, the **real** ledger library and the **real** migrations against a real `postgres:16`; only the build (`pnpm`), the service manager (`systemctl`) and the client (`psql`, which forwards to the real `psql` inside the container) are stood in for. It asserts four things: the deploy applies the pending migrations and the ledger records every one of them; a second deploy applies nothing and leaves the schema fingerprint unchanged; a migration that **cannot** apply STOPS the deploy, leaves the previous build in place and rolls back both the migration and its ledger row; and a deploy from an **older commit** applies nothing new and undoes nothing, so rolling the code back does not roll the schema back. `hosted/tests/deploy-applies-migrations-negative.sh` takes the migration step out of a copy of the tree and requires the gate to fail on the schema check specifically — with the deploy itself still working, so that it is not measuring the wrong thing | **Enforced by CI** — the `hosted-smoke` job runs both on every pull request; 19 assertions in the gate and 5 in the negative control, green 2026-11-04 |
| The nightly dump really leaves the box, and a copy to a second disk is compared with the dump | `hosted/scripts/off-host-copy.mjs` and `hosted/tests/backup-offhost-directory.sh` — the off-host copy was **Backblaze or nothing**: the nightly unit called the `b2` CLI directly, so a box without the CLI, a box still carrying the installer's placeholder credentials, or an operator who keeps their second copy on a NAS or a second disk had no off-host copy at all. There is now **one** implementation, `hosted/scripts/off-host-copy.mjs`, which the nightly unit calls and which resolves the destination itself — Backblaze B2, or a directory (`BROWNHILL_OFFHOST_DIR`) — and refuses a destination it cannot resolve rather than falling back to a placeholder path. The two TypeScript modules that used to describe this seam, `src/lib/backup/managed.ts` and `src/lib/backup/b2.ts`, had **no importers anywhere** and are gone; the README had pointed operators at them as the extension point. A directory copy is compared with the dump **file by file** afterwards, and the outcome is recorded in `_sync.json` as `{ok, at, target, targetKind, verified, detail}` — the state the operator's page reads. The page now distinguishes **Copied** (the copy was checked), **Copied, not verified** (a check was made and did not pass), **Failed** and **Not yet**; before, a box that had merely *attempted* a copy said "Copied" and nothing more. A state file written before the `verified` field existed reads as *"the check was not recorded"*, not as a failure — the two are not the same claim. The gate drives the **real** `hosted/bootstrap/brownhill-backup.sh` against a real directory: the dump and the WAL file land under `brownhill/<fqdn>/`, `cmp` proves them byte-for-byte identical, and the state says `ok: true`, `targetKind: "directory"`, `verified: true`. Its **negative control** points the destination at a path that cannot be a directory and requires the copy to fail, to fail loudly and to record `ok: false` — a gate that cannot fail is not a gate. The same rule holds for symlinks, on **both** sides of the copy: a dump holding one is **refused by name**, because following it would copy whatever it points at — a file elsewhere on the box, or a directory tree the dump has no business containing — and record the result as a copy of the dump; and a link standing at the destination is **replaced** by the real file or directory and reported in the state, because writing *through* it would put the bytes wherever it led instead of on the backup drive. Five unit tests cover this, each with a negative control: the file the link pointed at must come out **unchanged**, and the copy must not be recorded as successful | **Enforced by CI** — the `hosted-smoke` job runs it on every pull request that touches `hosted/**`; 13 assertions in the directory gate, 9 in the target gate and 24 unit tests over the helper, green 2026-11-04. Measured against the real volumes on the same date: the removable BROWNHILL drive is **exFAT**, which cannot hold a symlink at all — the operating system refuses to create one — so on that drive the destination-side attack cannot be mounted in the first place. The refusal of a symlinked *dump* is the protection that carries the weight, because the dump lives on the box's own filesystem, where links are ordinary. The same step is in the `hosted-smoke-production` job, which runs on the box when a human asks for it — but **no runner is registered** for that label, so it cannot run at all today (see "Gaps, named") |
| The address a request is counted against is the one the proxy saw, not the one the caller wrote | `src/lib/auth/client-ip.ts` and `tests/unit/client-ip.test.ts` — `X-Forwarded-For` is **appended** to by every proxy in the chain, so its first element is whatever the caller put there. The one-time-code endpoint throttled by the address it was given, and the address it was given was a header the caller wrote: a script could send a thousand addresses and be throttled a thousand times over, or send one address a thousand times and be throttled once. nginx now overwrites the header with the address it saw and adds `X-Real-IP` with the same value — in `hosted/nginx/brownhill.conf` and `hosted/dev/nginx.dev.conf`, so the two cannot disagree about which header the application reads — and the application reads `X-Real-IP` first and falls back to the **LAST** element of `X-Forwarded-For`, because nginx appends and so the last element is the one it saw. A forged leading element cannot displace it. The address is validated before it is used and bounded in length, so a header carrying a megabyte of text cannot become a megabyte of database. `tests/unit/client-address-contract.test.ts` walks the source and fails the build if any module reads either header itself — the list grows as the code that needs the address grows, and the gate grows with it — and `tests/integration/auth/otp-address.test.ts` and `tests/integration/auth/sign-submit-address.test.ts` prove the two endpoints that act on it | **Enforced by CI** — the `unit-tests` job, on every pull request; 17 unit tests and 5 integration tests, green 2026-11-05. The integration file builds the vehicle, the driver, the agreement and the signing session it needs, because the `hosted-smoke` job's database is **provisioned but never seeded** — the demo fleet belongs to the `a11y` job's seed — so a test that reads a row it did not write fails on CI while passing on a developer's seeded machine |
| The application's SQL and the migrations are held to each other, and the database is asked before it serves anything | `src/lib/schema-contract.ts` and `tests/unit/schema-contract.test.ts` — the application and the migrations are two halves of one thing, and nothing held them to each other: a table renamed in a migration and a query that still used the old name were both perfectly good TypeScript, and the failure arrived as a 42P01 at run time, on the customer's own box, on the screen somebody was using. | The application knows its own address, and never falls back to localhost | `src/lib/app-url.ts` and `tests/unit/accounting/mtd-route.test.ts` — the HMRC integration built its redirect URI and its filing addresses from `NEXT_PUBLIC_APP_URL`, read at the module level, and fell back to `http://localhost:3000` when the variable was not set. On the hosted box — where the application is reachable at the customer's own hostname and nowhere else — that fallback pointed HMRC at a machine that does not exist and the operator at a page that 404s, and the page printed the same address back to the operator, so the failure looked like a configuration mistake on their side rather than a fallback in ours. `src/lib/app-url.ts` is one function, and it answers the address of THIS deployment: the configured value first, because behind a proxy the request's own host is not what the customer types into their browser, and the forwarded headers second. **Null when neither is available** — the caller then says so rather than inventing an address. The function is `async` because the headers are read per request, and the value is never cached across requests, so a deployment whose address changed does not keep publishing the old one. The connection card and the overdue check both read it, and the address is shown on the page before the operator connects anything | **Enforced by CI** — the `unit-tests` job, on every pull request; 6 new tests across the two HMRC suites — 4 in the route and 2 in the submit — green 2026-11-05 |

## Why this repo has no `docs/product/` upstream

The upstream project (`elite-fleet-management`) is the multi-tenant SaaS. This
repo is the **Brownhill-only mirror**: a single-tenant, self-hosted deployment
of the same application. The upstream keeps its planning documents private;
this repo ships the operator-facing ones (`docs/runbook/`, `docs/testing/`) and
now this product set.

Consequence worth stating plainly: **the SaaS monetisation model is not
Brownhill's monetisation model.** Brownhill buys the software once and operates
it; it does not pay a per-seat subscription. Documents 7, 9 and 10 are
therefore about a *business*, not a *licence* — see the decision sections
inside each.

## The two product lines in this repository

Both run the same `src/` tree. `DEPLOYMENT_PROFILE` gates the difference at
compile time.

| | **Brownhill Fleet (this repo)** | **Elite Fleet Management (upstream)** |
| --- | --- | --- |
| Shape | Single tenant per deployment | Multi-tenant SaaS |
| Tenancy | One `tenant_id`, seeded at bootstrap | Many, isolated by RLS |
| Where it runs | Namecheap Business VPS Pulsar, Ubuntu 24.04, Postgres 16.4 + PostgREST 12.2.3 + nginx | Vercel + Supabase |
| Auth | Local HS256 JWT against PostgREST | Supabase Auth |
| Entitlement source | `PROFILE_MODULES` for the deployment profile | `plans` / `add-ons` tables |
| Who pays | Brownhill, once, to its own hardware | The operator, per tenant, per period |

## How to keep this honest

- A change that invalidates a document changes that document **in the same
  commit** as the code. A doc edit that trails the code is a promise, and the
  gap between the promise and the doc is where a stale document lives.
- Before declaring a build task complete, re-open this file and make the
  statuses and dates true.
- When a figure changes, grep the set for the old one and fix every
  occurrence. Two documents quoting different numbers is worse than one
  document quoting nothing.
