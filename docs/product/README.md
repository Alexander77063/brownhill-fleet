# Brownhill Fleet — product foundation

The ten documents every Brownhill Fleet project carries. This file is the
index: it says what each document is for, when it was last checked against
the code, and where its gaps are.

**Last audited against the code: 2026-11-01**, on `feat/handover-hardening`
(fork `Alexander77063/brownhill-fleet`; fork base `7e1e458`, audited
against `16cf49d` and the changes committed alongside this audit). The migration
replay, the bootstrap idempotency gate, the environment-variable gate, the
bootstrap-waiter gate and the portability-guards gate below were all run
against a scratch Postgres on the same date. The portability proof and the
chain-assertion negative gate were run against the **live hosted stack** on
the same date — the first time assertion 14 (the TLS chain) or assertion 15
(the tenant-mismatch 403) have ever executed anywhere. The no-credential
gate, its negative gate and the acceptance bar's own arithmetic were run
against the working tree on the same date; the no-credential gate is the
first of the three that had never run at all, and its first run found a
rule in it that could not fail. The two restore gates — the one that proves
a restore survives the application's stop, and the one that proves the
privilege contract — were run against the working tree on the same date;
both had never run at all, and the first run of the first of them failed
against the restore script as it stood. The accessibility gates — the form
audit, the ESLint pass and the contrast test — were run against the working
tree on the same date; the contrast test had never existed, and the first run
of the contrast gate found a colour that failed AA. The three sign-in and
recovery gates — reachability, method choice and the operator's password
reset — were run against the working tree on the same date; all three had
never run at all, and each one found a defect on its first run: the sign-in
pages were unreachable, the hosted build offered a sign-in method it could
not honour, and a forgotten password had no recovery route inside the app.

On **2026-11-01** the tree was audited again for the deployment's own
settings. Two new gates were written and run against the working tree, and
both found the defect they were written for on their first run: the settings
the application reads were not provided by anything on the box, under three
of the five names the handover gave, and the redirect pointed at a path the
application does not serve. The unit test for the password reset was
extended to 44 tests, covering the rule that a database which could not be
reached must raise rather than read as an empty table.

On the same date the **deployment gate** was audited, and it was the worst
of the three kinds of finding: a safety net with no call site. The table
that decides which URL prefixes a build does not serve had never been
consulted by anything, so the cross-tenant console, the SaaS's own signup
form and the subscription API were all reachable on a box that must serve
none of them. It is now wired into the middleware, with a 34-test boundary
and an 8-check negative gate. One prefix was **removed** from the table
rather than added: `/ops/billing` carries the operator's rent collection,
and gating it would have taken the arrears table, the driver's payment link
and the receipt form with it.

On the same date the **accounting module** was audited, and it turned up the
defect that matters most in this repository: a posting to the ledger could
leave half of itself behind. `accounting.journal_lines` carries a **deferred**
balance trigger, so an entry is judged at COMMIT and only there is the
balance meaningful — and the bridge was writing its entry, its lines and its
audit row as three separate autocommitted statements, so the trigger fired
after the **first** line, judged that line alone, and rejected the entry. The
entry row, committed before the lines were attempted, stayed behind as an
orphan with no lines. Measured against a real postgres:
`journal <id> unbalanced: debits=120 credits=0`. Three call sites took that
path — the reconciliation queue's "mark as a VAT payment" and "mark as a bank
fee" buttons, and the MTD VAT submission — and all three failed with a 500
while leaving the orphan behind. The bridge now takes a transaction handle as
a **required first argument**, so a call site that forgets one does not
compile. The same audit found that the accounting schema's tenant isolation
was **unproven**: migrations 0068 and 0069 had shipped policies that only
asked whether *some* tenant was pinned on the session and never compared the
row's tenant with the caller's — the same "a policy that merely looks right"
failure the migrations themselves describe. Both are now proved against a
real postgres, and the database-backed tests **actually run in CI** for the
first time.

The gate does not take the code's word for it: it watches the target path **while the write is in progress**, with the write deliberately slowed, and requires every observation of it to be the complete file **at mode 0640** — the size and the mode together, because a credential that is world-readable for the length of one `chown` and one `chmod` has been exposed, and nothing checked that: the old check looked at the file afterwards, by which time the trailing chmod had put the mode back. The gate itself was wrong until 2026-11-01, when it **failed the `unit-tests` job on the fast Linux runner and nowhere else**: it stopped watching the moment it saw the writer's stop-marker, and it checked that marker *before* looking at the target path, so on a machine where the rename and the marker fall inside one poll interval it never saw the file at all — a correct writer reported as a failure, and a Windows checkout passed only because the poll happened to land in the gap. `hosted/tests/secret-file-permissions-negative.sh` runs the same gate against three copies of the tree, each carrying one of the faults, and requires it to fail on the right check each time — including the one that widens the file on its way to the target path, which the gate previously could not have caught at all | **Enforced by CI** — the `unit-tests` job, on every pull request; 12 checks plus 8 checks in the negative gate, green 2026-11-01 |
| A build only serves the surfaces it actually has | `tests/unit/deployment-gate.test.ts` over `src/lib/deployment/gate.ts` and `src/middleware.ts` — the table that decides which URL prefixes a deployment profile does not serve **had no call site anywhere in the repository**. It was complete, correct-looking, and never consulted, so on Brownhill's box the cross-tenant super-admin console (`/platform`, 22 routes), the SaaS's own self-serve signup form (`/request-access`, which rendered the upstream's "Elite Fleet Management" branding and its "Multi-tenant · White-label · UK-ready" footnote on a build that is neither multi-tenant nor white-label) and the subscription-to-us API were all reachable. The sign-in page already promised the block — on a build the customer already owns, "a link to /request-access would 404" — and nothing delivered it. The gate now runs in the middleware, **before auth and before the `customerOps` early return**, because it is a property of the profile rather than of the operator surfaces: `saas` has no vehicle-owner portal, so `/owner` is closed there too. One prefix was **removed** from the table rather than added: `/ops/billing` is the page carrying Brownhill's arrears table, the driver's payment link and the receipt form, and gating it would have taken the rent collection with it — the subscription half of that page hides itself through `payFirst()`, which is false in the UK. `/api/payments/*` and `/api/webhooks/*` are never gated, because gating them stops the customer getting paid. `hosted/tests/deployment-gate-negative.sh` runs the test against a gate that blocks nothing and against one that blocks everything, and requires it to fail on the right family of checks each time | **Enforced by CI** — the `unit-tests` job, on every pull request; 34 tests plus 8 checks in the negative gate, green 2026-11-01 |
| A posting to the ledger lands whole, or lands not at all | `tests/unit/accounting/journal-bridge-transaction.test.ts` and `tests/integration/accounting/journal-atomicity.test.ts` — `accounting.journal_lines` carries a **deferred** balance trigger, so an entry is judged at COMMIT and only there is the balance meaningful. The bridge wrote its entry, its lines and its audit row as three separate autocommitted statements on a pooled connection, so the trigger fired after the **first** line, judged that line alone, and rejected the entry — while the entry row, committed before the lines were attempted, stayed behind as an **orphan** with no lines. Measured against a real postgres: `journal <id> unbalanced: debits=120 credits=0`. Three call sites took that path — the reconciliation queue's "mark as a VAT payment" and "mark as a bank fee" buttons, and the MTD VAT submission — and all three failed with a 500 while leaving the orphan behind. The bridge now takes a transaction handle as a **required first argument**, so a call site that forgets one does not compile: `pnpm typecheck` is the enforcement. The unit test proves the handle is written through rather than ignored; the integration test proves the resulting behaviour against the real schema — a balanced entry commits with every line and its audit row, an unbalanced one commits **nothing** — and a third case reproduces the old behaviour deliberately and asserts the orphan really does appear, so the other two cannot be passing for the wrong reason | **Enforced by CI** — the `hosted-smoke` job runs the integration suite against the compose stack's postgres; 4 unit tests plus 3 integration tests, green 2026-11-01 |
| One tenant's ledger is invisible to another tenant's | `tests/rls/accounting-rls.test.ts` (`pnpm test:rls`) — the accounting schema is not exposed by PostgREST and the application's own connection is the superuser, which **bypasses** row-level security, so for the application's queries the tenant has to be named in the SQL (checked statically by `tests/unit/accounting/sql-contract.test.ts`). That left the database's own second line of defence unproven — and migrations 0068 and 0069 had shipped policies that only asked whether *some* tenant was pinned on the session and never compared the row's tenant with the caller's, which is the "a policy that merely looks right" failure the migrations themselves describe. The suite proves: no browser-facing role can reach the accounting schema at all; row-level security is enabled on every tenant-scoped table and every one of them carries the restrictive `tenant_isolation` policy, the two sets being exactly the same set; the audit log has no permissive policy that could rewrite it; a member of one tenant sees none of another's ledger, and a caller with no identity at all sees nothing. The last two checks are **negative controls** — the restrictive policy is dropped inside a transaction and the isolation is required to leak, and a permissive DELETE policy is added and the audit trail is required to go | **Enforced by CI** — the `hosted-smoke` job; 9 tests, green 2026-11-01, and watched **failing** (3 of 9) with the policy dropped from the live database and restored afterwards |
| The database-backed tests actually run in CI | `.github/workflows/hosted-smoke.yml` — the job's `paths` filter named the schema, the scripts and the hosted box, and **nothing under `src/`**, so a change to the ledger's own code never brought the job up; and its test step ran `pnpm test` with no `DATABASE_URL`, so both database-backed suites **skipped** — loudly, but a skip is not a pass, and the job went green while the ledger's atomicity and the accounting schema's tenant isolation were never executed anywhere in CI. The filter now names the accounting module, the API routes under it, the database helper and the two test directories, and the test step is given the compose stack's own `postgres://postgres@127.0.0.1:55432/postgres` | **Enforced by CI** — the command was run end to end against the running compose stack on 2026-11-01: **562 tests passed, 2 skipped, 0 failed**, the 12 database-backed ones included |

## Why this repo has no `docs/product/` upstream

The upstream project (`elite-fleet-management`) is the multi-tenant SaaS. This
repo is the **Brownhill-only mirror**: a single-tenant, self-hosted deployment
of the same application. The upstream keeps its planning documents private;
this repo ships the operator-facing ones (`docs/runbook/`, `docs/testing/`) and
now this product set.

Consequence worth stating plainly: **the SaaS monetisation model is not
Brownhill's monetisation model.** Brownhill buys the software once and operates
it; it does not pay a per-seat subscription. Documents 7, 9 and 10 are
therefore about a *business*, not a *licence* — see the decision sections
inside each.

## The two product lines in this repository

Both run the same `src/` tree. `DEPLOYMENT_PROFILE` gates the difference at
compile time.

| | **Brownhill Fleet (this repo)** | **Elite Fleet Management (upstream)** |
| --- | --- | --- |
| Shape | Single tenant per deployment | Multi-tenant SaaS |
| Tenancy | One `tenant_id`, seeded at bootstrap | Many, isolated by RLS |
| Where it runs | Namecheap Business VPS Pulsar, Ubuntu 24.04, Postgres 16.4 + PostgREST 12.2.3 + nginx | Vercel + Supabase |
| Auth | Local HS256 JWT against PostgREST | Supabase Auth |
| Entitlement source | `PROFILE_MODULES` for the deployment profile | `plans` / `add-ons` tables |
| Who pays | Brownhill, once, to its own hardware | The operator, per tenant, per period |

## How to keep this honest

- A change that invalidates a document changes that document **in the same
  commit** as the code. A doc edit that trails the code is a promise, and the
  gap between the promise and the doc is where a stale document lives.
- Before declaring a build task complete, re-open this file and make the
  statuses and dates true.
- When a figure changes, grep the set for the old one and fix every
  occurrence. Two documents quoting different numbers is worse than one
  document quoting nothing.
